/plan 模式：先出图纸，再动砖头

2026 · April Claude Code · /plan · 方案规划

用过 Claude Code 的人大多遇到过这种情况：需求一发，它直接开始写代码，写完才发现方向跑偏了。

问题不在于它能力不够，而在于 LLM 的工作机制——它在收到指令的瞬间就开始生成，不会主动停下来确认理解是否一致。/plan 模式就是为了解决这个问题而设计的。

/plan 模式的底层逻辑

正常对话模式下，Claude Code 的执行路径是：收到指令 → 立即写代码。

/plan 模式改变了这个路径，变成：收到指令 → 探索分析 → 输出方案 → 等待批准 → 执行。

关键在"等待批准"这一步。批准之前，它不会修改任何文件。

这个设计背后的逻辑是：在执行层面的返工成本，远高于在规划层面的修改成本。改一份文字方案只需要一句话，改已经写好的代码可能要推倒重来。/plan 把对齐的成本前置，规避了执行阶段的高代价返工。

用 /plan 开发一个 App 的完整流程

第一步：进入 plan 模式并描述需求

/plan 帮我做一个本地记账小工具，支持：
- 手动输入收支记录
- 按类别统计（餐饮/交通/娱乐）
- 导出 CSV

发出后，Claude Code 进入 plan 模式，此后只做分析，不动代码。

第二步：Claude Code 主动探索

这一阶段，它会做两件事：

读懂现有项目（如果是已有项目）：扫描文件结构，理解已有代码的技术栈、目录组织、依赖关系，确保方案与现有代码兼容，不会引入冲突。

通过反问澄清需求（如果描述不够明确）：比如"是命令行界面还是图形界面？""存储用文件还是数据库？"这些问题在规划阶段回答，比在代码写了一半时再改要省事得多。

第三步：输出实施方案

探索完成后，它会给出结构化的方案，包括技术选型、文件结构、实施步骤：

实施方案

技术栈：Python + SQLite + Click（命令行界面）

文件结构：

- main.py：程序入口

- db.py：数据库操作封装

- export.py：CSV 导出逻辑

实施步骤：

1. 初始化数据库，建 transactions 表

2. 实现 add / list / summary 命令

3. 实现 export 命令

在这一步，你可以直接修改方案。说"不要用 Click，改成普通输入"，它调整方案；说"存储改用 JSON 文件"，它重新规划。方案确认后，你给出批准指令，它才开始写代码。

第四步：按方案执行

退出 plan 模式后，Claude Code 按照已确认的方案逐步实现。因为核心决策已经在规划阶段对齐，执行过程中的偏差通常只停留在细节层面，不会出现方向性错误。

什么时候用 /plan 更合适

不是所有任务都需要 /plan。改一个小 bug、加一个单独函数，直接说就行。

以下几类场景，开 /plan 会明显减少返工：

从零起新项目：技术栈、目录结构、依赖关系都没定，先出方案确认方向，比写完才发现框架选错了要好。

多文件联动改动：重构模块、加跨越前后端的功能——影响范围大，规划阶段先列清楚哪些文件会变、变什么，比执行到一半发现漏掉关键依赖更安全。

需求描述不清晰：知道想要什么结果，但说不清楚技术路径。进 plan 模式，通过它的反问把需求结构化，比自己干想要快，也比描述不清就让它动手要准确。

重构：重构的核心风险是"改了不该改的地方"。方案阶段明确影响边界，执行时更可控。

和直接执行的本质区别

直接发指令：对齐成本在执行之后——发现不对，返工。

用 /plan：对齐成本在执行之前——方案不对，改方案。

两者的时间总量不一定差多少，但后者的不确定性更低。对复杂任务来说，把高代价的"代码返工"换成低代价的"方案修改"，是更合理的工程决策～
